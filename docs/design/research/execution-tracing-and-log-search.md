# Tracing research: correlation, causation, and log search for a Python trading system

Scope: feed -> Redis Streams bus -> strategy processes -> OMS -> RMS -> broker. JSON-lines logs already exist with fixed fields: ts, level, logger, event, msg, event_id.

## 1. correlation_id / causation_id / actor pattern (event sourcing / CQRS)

**Greg Young's canonical definition** (from a 2013 dddcqrs mailing-list thread, quoted verbatim across the ecosystem):

> "Let's say every message has 3 ids. 1 is its id. Another is correlation, the last is causation. If you are responding to a message, you copy its correlation id as your correlation id, its message id is your causation id. This allows you to see an entire conversation (correlation id) or to see what causes what (causation id)."
Source: https://groups.google.com/g/dddcqrs/c/qGYC6qZEqOI (Greg Young's reply; also reproduced at https://blog.arkency.com/correlation-id-and-causation-id-in-evented-systems/ and https://railseventstore.org/docs/core-concepts/correlation-causation)

Exact rule, worked example from the same thread:
- Every message has `MessageId`, `CorrelationId`, `CausationId`.
- When responding to message X: `new.CorrelationId = X.CorrelationId`, `new.CausationId = X.MessageId`.
- A saga/process manager that starts because of an event gets a **new** CorrelationId scoped to that process's own "conversation" (Young: "every time we start a process, the correlation id changes... each of the processes is a distinct conversation").
- Chain example given in the thread (signal -> intent -> order -> fill style chain):
  ```
  A (command)   messageId=1  causationId=3   correlationId=4
  B (event)     messageId=5  causationId=1   correlationId=4   # response to A
  C (saga event)messageId=6  causationId=5   correlationId=4   # saga created from B
  D (command)   messageId=8  causationId=6   correlationId=4   # saga issues D
  E (event)     messageId=10 causationId=8   correlationId=4   # response to D
  ```
  Rule of thumb that resolves the thread's ambiguity: causationId is always the MessageId of the message you are **directly and synchronously responding to at this handler step**, not an ancestor further back.

**EventStoreDB / Kurrent docs** — reserved metadata keys, written under `metadata.$correlationId` / `metadata.$causationId` (note the `$` prefix, since `$`-prefixed names are reserved):
Source: https://docs.kurrent.io/server/v24.10/features/streams.md (also https://github.com/kurrent-io/ESDB-Docs-v5/blob/main/docs/streams.md)
- `$correlationId`: "The application-level correlation ID for the message."
- `$causationId`: "The application-level causation ID for the message."
- A built-in system projection `$by_correlation_id` links every event carrying a given `$correlationId` into a stream `$bc-{correlation_id}`, giving you the whole "conversation" for free once the projection is enabled: https://github.com/kurrent-io/ESDB-Docs-v5/blob/main/docs/projections.md
- Practical write format confirmed by Greg Young in the EventStore mailing list: `{"metadata": {"$correlationId": "id", "$causationId": "id"}}` posted with the `events+json` media type. Source: https://groups.google.com/g/event-store/c/1b5eNaQH1Mo

**Microsoft's framing (actor/initiator + saga chain across services)**:
- Azure Architecture Center, Event-Driven Architecture Style: "include a correlation ID in every event so that all downstream consumers and logging systems can connect related operations into a single trace. Plan for this instrumentation from the start of the design, because retrofitting observability into a decoupled system is substantially more difficult than building it in."
  Source: https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/event-driven
- Azure Architecture Center, Saga pattern: describes choreography (each local transaction publishes an event that triggers the next) vs. orchestration (a central orchestrator issues commands and tracks state) — this is the shape of your feed->strategy->OMS->RMS->broker chain. Source: https://learn.microsoft.com/en-us/azure/architecture/patterns/saga
- Microsoft's Engineering Fundamentals Playbook gives the operational checklist: assign correlation id at the first external interaction, propagate to every downstream component, log it everywhere, and explicitly recommends OpenTelemetry as the way to get this "out of the box" via TraceId. Source: https://microsoft.github.io/code-with-engineering-playbook/observability/correlation-id/

**How this maps onto your chain** (signal -> order intent -> order -> fill):
- `correlation_id`: assigned once, at the signal (the first thing that starts the "conversation" — e.g., a market data tick or a strategy's periodic evaluation that decides to act). Copied unchanged onto every downstream message/log line: order intent, order, ack, fill.
- `causation_id`: at each hop, set to the `event_id`/`message_id` of the specific message that directly triggered this one. Signal's causation_id may be null or the triggering market data event_id; order intent's causation_id = signal's event_id; order's causation_id = order intent's event_id; fill's causation_id = order's event_id (or the venue ack's event_id if there's an intermediate ack step).
- `actor` / initiator: not part of Young's 3-id scheme — add it yourself as a 4th field identifying *who or what* originated the correlation_id's conversation (e.g., `strategy_id`, `"manual"`, `"risk_kill_switch"`, a user id). This is standard practice layered on top of correlation/causation in most production implementations (see Rails Event Store's metadata pattern, which allows arbitrary extra metadata fields alongside `correlation_id`/`causation_id`: https://railseventstore.org/docs/core-concepts/correlation-causation).

## 2. W3C Trace Context + OpenTelemetry over a message bus (Redis Streams)

**W3C Trace Context spec** (https://www.w3.org/TR/trace-context/):
- Two headers: `traceparent` (required) and `tracestate` (optional, vendor-specific).
- `traceparent` format: `version-trace-id-parent-id-trace-flags`, e.g. `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`. `trace-id` identifies the whole distributed trace; `parent-id` is the ID of the span/operation that produced this header value.
- Every hop that forwards the message MUST propagate `traceparent`/`tracestate` unchanged (or update `parent-id` to represent its own new span) — "forwarding" vs. "participating" in a trace.
- Designed for HTTP headers but the value format is transport-agnostic; anything with a key-value "header-like" carrier (including a Redis Streams field) can carry it.

**OpenTelemetry messaging semantic conventions** (https://opentelemetry.io/docs/specs/semconv/messaging/messaging-spans/, backing OTEP: https://github.com/open-telemetry/oteps/blob/main/text/trace/0205-messaging-semantic-conventions-context-propagation.md / 0220):
- Defines a "message creation context": the producer creates a Create/Send/Publish span and injects its context into the message so a consumer's Process/Receive/Deliver span can link back to it, regardless of transport.
- "A producer SHOULD attach a message creation context to each message. If possible, the message creation context SHOULD be attached in such a way that it cannot be changed by intermediaries."
- OTel does not mandate a specific serialization mechanism for injecting context into non-HTTP transports; it defers to transport-specific conventions or manual injection via `opentelemetry.propagate.inject()`/`extract()` writing/reading a `traceparent` field.

**Redis Streams specifically — no dedicated official instrumentation**:
- `opentelemetry-instrumentation-redis` (PyPI: https://pypi.org/project/opentelemetry-instrumentation-redis/, docs: https://opentelemetry-python-contrib.readthedocs.io/en/latest/instrumentation/redis/redis.html) instruments the **redis-py client commands** (GET/SET/XADD/XREADGROUP etc. as generic DB-client spans) — it does NOT understand Redis Streams semantically (no producer/consumer context propagation, no stream-aware "Create"/"Process" spans). It will show you "an XADD happened" as a span, not link producer and consumer traces.
- To actually get producer->consumer trace correlation across Redis Streams you must do it by hand: `inject()` a dict carrier with `traceparent`/`tracestate` and store those as extra fields in the `XADD` payload (alongside your real message fields); on the consumer side, `extract()` those fields from the `XREADGROUP` result and use the resulting context as the parent when starting your own span. Worked end-to-end code example (produce_message / process_messages with XADD/XREADGROUP, tracer spans with `messaging.system=redis`, `messaging.redis.stream`) is here: https://oneuptime.com/blog/post/2026-02-06-trace-redis-streams-opentelemetry/view — this is a third-party blog, not an official OTel doc, precisely because there is no first-party Redis Streams semantic-convention module (only generic "messaging" semconv + generic redis client instrumentation exist).
- redis-py 5.x also ships a **native** OTel *metrics* integration (`redis.readthedocs.io/en/stable/opentelemetry.html`) for connection-pool/command/streaming metrics (e.g. `redis.client.stream.lag`), but that is metrics, not trace-context propagation, and is separate from the tracing question.

**Cost/complexity verdict for a two-person team**: Full OTel (SDK + exporter + collector + backend like Jaeger/Tempo, plus manually wiring inject/extract around every XADD/XREADGROUP call because there's no Streams auto-instrumentation) is real, ongoing infrastructure and code-maintenance burden for a 2-person shop. **Plain ids in the envelope are enough** for this system's actual need — full W3C traceparent/OTel spans buy you cross-service latency breakdowns and vendor-agnostic trace visualization, which are not the stated goal here ("traceable back to what caused it and who initiated it"). A flat `correlation_id` + `causation_id` + `actor` triple in the JSON envelope, queryable with grep/jq/DuckDB, achieves the traceability goal at near-zero infra cost. Adopt OTel only if/when you need cross-process latency profiling or plan to plug into a real APM backend.

## 3. Nautilus Trader's identifiers and structured logging (reference architecture)

Source: https://nautilustrader.io/docs/latest/concepts/logging/, https://nautilustrader.io/docs/latest/concepts/events/, https://nautilustrader.io/docs/latest/concepts/reports/, https://nautilustrader.io/docs/python-api-latest/model/identifiers.html

Identifiers:
- `trader_id`: the trader/deployment instance identifier, e.g. `TESTER-001`.
- `instance_id`: a UUID4 unique to this **runtime process instance** (regenerated each run) — distinguishes log lines from two different runs of the same trader_id.
- `strategy_id`: identifies which strategy logic created/owns an order or position.
- `client_order_id`: the client-assigned order identifier (their equivalent of FIX ClOrdID), the index/join key across order events.
- `venue_order_id`: the venue-assigned order ID once the order is accepted (their equivalent of FIX OrderID), populated only after acceptance.
- `account_id`: account the order/position belongs to.
- `position_id`: for `NETTING` OMS, deterministically derived as `{instrument_id}-{strategy_id}`; for `HEDGING` OMS, a distinct custom id.
- `exec_spawn_id`: when an execution algorithm splits one parent order into child orders, every child carries `exec_spawn_id` = the parent's `client_order_id`, plus a `spawn_sequence` number — this is their parent/child order-splitting lineage mechanism. Source: https://github.com/nautechsystems/nautilus_trader/blob/bd39a3af/docs/concepts/execution.md

Every order **event** (OrderInitialized, OrderSubmitted, OrderFilled, etc.) carries: `trader_id`, `strategy_id`, `instrument_id`, `client_order_id`, `event_id` (unique per event), `ts_event` (when it happened, ns), `ts_init` (when the event object was created, ns) — i.e., a fixed identifying envelope on every event regardless of type, with type-specific extra fields layered on (`venue_order_id`, `account_id`, `last_qty`/`last_px`/`trade_id`/`commission` on fills). Source: https://nautilustrader.io/docs/latest/concepts/events/

Structured logging: log file naming already bakes in `trader_id` and `instance_id` — `{trader_id}_{datetime}_{instance_id}.{log|jsonl}` — so you can identify which trader/run produced a log file before even opening it. JSON-lines output is a native `LoggerConfig(file_config=FileWriterConfig(file_format="json"))` option. Source: https://nautilustrader.io/docs/latest/concepts/logging/

**Takeaway for this team**: Nautilus's four-tier identifier model (`trader_id`/`instance_id` for "which deployment, which run" + `strategy_id` for "who initiated" + `client_order_id`/`venue_order_id` for "which order, at which stage" + `event_id` per event) is a close match for what's being asked for here, and validates the shape of the recommendation below.

**Recommendation for "docker compose on one 8GB machine, two developers": VictoriaLogs.**
Rationale: it is the only option that gives you (a) an actual indexed, arbitrary-field query language (LogsQL) suitable for `correlation_id`/`causation_id`/`actor` lookups, (b) genuinely tiny RAM/disk footprint benchmarked as far lighter than Loki or Elasticsearch, explicitly designed to run comfortably on constrained hardware, and (c) a single-container docker-compose footprint with no separate indexing-label design tax the way Loki has. Loki's label-cardinality constraint works against exactly the field you most want to filter on. Seq's 3.5GB RAM floor is expensive on an 8GB box also running the trading stack, and its ingestion model assumes Serilog/CLEF rather than arbitrary JSON-lines. Keep **jq** and **DuckDB** in the toolbox regardless — jq for quick `tail -f | jq` triage, DuckDB for retrospective multi-file causal-chain reconstruction via SQL joins on `correlation_id` — they're free, zero-setup complements rather than alternatives to a log server.

## 5. Order lifecycle logging conventions (public examples)

**FIX Protocol** (the industry-standard vocabulary; source: https://fix.dev/organizations/fix-standards/specs/1000002/fields/11, https://orchimate.org/fixtrading/fix-4.2/fields):
- Tag 11 `ClOrdID`: "Unique identifier for Order as assigned by the buy-side... Uniqueness must be guaranteed within a single trading day." — this is your strategy/OMS-side order id, equivalent to Nautilus's `client_order_id`.
- Tag 37 `OrderID`: "Unique identifier for Order as assigned by sell-side (broker, exchange, ECN)." — the venue/broker-assigned id, equivalent to `venue_order_id`.
- Tag 41 `OrigClOrdID`: "ClOrdID of the previous order... used to identify the previous order in cancel and cancel/replace requests." — this is FIX's causation-style link for order amendments (cancel/replace chains).
- Confirmed relationship/flow (Stack Overflow, corroborating fix.dev field defs): NewOrderSingle carries `ClOrdID`; broker's ExecutionReport echoes that `ClOrdID` and adds its own `OrderID`; a later CancelReplaceRequest sets `OrigClOrdID` = the previous `ClOrdID` and issues a new `ClOrdID` for the replacement. Source: https://stackoverflow.com/questions/14587000/what-is-the-relationship-between-the-fix-protocols-ordid-clordid-origclordid

**Broker/venue audit-trail examples** (what production systems actually persist, beyond FIX tags):
- Trading Technologies audit trail reference includes, per order-related record: `Client` (account/customer short code), `ClOrderID`, `TTOrderID` (their venue-assigned id), and `ParentID` ("TT-generated ID that uniquely identifies a parent order... associated with all of its child orders" — e.g. for an Iceberg order's child slices). Source: https://library-staging.tradingtechnologies.com/trade/order-management/audit-trail/reference-audit-trail/audit-trail-reference/
- Cboe Digital / ErisX audit trail layout: `ClOrdId` (tag 11), `OrderID` (tag 37), `OperatorId` (tag 50 — "value used to identify the **user** that entered the order" — this is the actor/initiator field), and the prior `ClOrdID` for replace chains. Source: https://www.erisx.com/wp-content/uploads/2024/03/Audit_Trail_Information_Document_v1.0.pdf
- SEC/FINRA CAT (Consolidated Audit Trail) technical spec formalizes the same shape at regulatory scale: every event carries `orderID` (internal, unique when combined with date+firm+symbol), `parentOrderID` (links child order-splitting/routing events back to the parent), `priorOrderID` (links replace-chain predecessor), a `firmDesignatedID` (FDID, required on all New Order events — this is the actor/customer-identifying field), and `CATReporterIMID`/`senderIMID`/`receiverIMID` for cross-firm routing linkage. Source: https://catnmsplan.com/sites/default/files/2020-09/09.09.20-CAT_Reporting_Technical_Specifications_for_Industry_Members_v2.2.1r7_CLEAN_2.pdf
- A practitioner write-up on FIX audit-trail design makes the key operational point directly relevant to a two-person team: "To reconstruct [an order's lifecycle] later, you need every message in the exchange, correctly linked (ClOrdID, OrigClOrdID, OrderID, ExecID), with trustworthy timestamps... capture the audit stream where the messages actually cross the wire, not only where decisions are made" (i.e., don't rely solely on the OMS's own internal log as the system of record — also capture at the transport boundary, e.g. right where you talk to the broker). Source: https://dev.to/andrewa/the-audit-trail-problem-hiding-in-your-fix-connectivity-layer-38ao

**Synthesized field list an order log line should carry** (cross-referencing FIX + Nautilus + CAT + this team's existing envelope):
- `client_order_id` (= FIX ClOrdID = Nautilus client_order_id): your own id for the order, assigned at OMS/strategy layer.
- `venue_order_id` (= FIX OrderID = Nautilus venue_order_id): broker/venue-assigned id, populated once accepted; null/absent before ack.
- `orig_client_order_id` (= FIX OrigClOrdID): only on amend/cancel-replace lines, pointing at the previous client_order_id in the chain.
- `strategy_id`: which strategy logic generated the order (your "who/what initiated" at the strategy layer — matches Nautilus and this vault's `actor` concept).
- `parent_intent_id` / `correlation_id`: the id of the upstream order intent / signal that caused this order — your causation/correlation chain from section 1, not present in FIX itself but this is the layer FIX doesn't cover (FIX only links order-to-order via OrigClOrdID, not signal-to-order).
- `account_id` / `book`: which account/book the order settles against (present in every source above as `Client`/`account_id`/CAT's FDID).
- `event_id`: unique id for this specific log line/event (you already have this).
- `ts_event` vs `ts_init` (Nautilus's distinction) or FIX's requirement for "trustworthy timestamps" on every leg — worth keeping both "when it happened" and "when we logged it" distinct if there's any risk of delayed/replayed processing.

## Recommendation

**Minimal envelope additions** (on top of existing `ts, level, logger, event, msg, event_id`):
- `correlation_id` — set once at the true origin of a causal chain (a market-data signal, a scheduled strategy evaluation, or a manual/human action) and copied unchanged onto every downstream log line/event in that chain (order intent -> order -> ack -> fill, and any RMS check in between).
- `causation_id` — set on every line to the `event_id` of the specific message that directly and immediately triggered this one (one hop back, not the chain root).
- `actor` — who/what initiated the correlation_id's chain: a `strategy_id`, `"manual:<user>"`, `"risk_kill_switch"`, etc. Not part of Young's original 3-id scheme but standard practice layered on top (matches Nautilus's `strategy_id` and FIX/CAT's `OperatorId`/FDID role).
- For order-specific log lines specifically, also carry: `client_order_id`, `venue_order_id` (once known), `orig_client_order_id` (on amends), `account_id`/`book`, and `parent_intent_id` (= your `causation_id` pointing at the order-intent event, kept as an explicit alias if that's clearer downstream than reading it off a generic causation_id field).

**Where to generate ids**: `correlation_id` at the earliest point a decision chain starts (feed signal handler or strategy's decision function) — generate it there and pass it down through every function call / Redis Streams message / RMS check / broker call, never regenerate it downstream. `causation_id` and `event_id` are generated fresh at each hop, right where that hop's own log line / outgoing message is constructed (event_id = this message's own id; causation_id = the incoming message's event_id that this handler is reacting to). Use UUID4 (or ULID for sortability) for all three; no central id-issuing service is needed for a system this size — one process assigning its own ids and copying forward the correlation_id it received is sufficient, exactly as EventStoreDB/Rails Event Store do.

**Do not adopt full W3C Trace Context / OpenTelemetry now.** There's no ready-made OTel Redis Streams instrumentation (you'd hand-roll inject/extract around every XADD/XREADGROUP), and the operational payoff (cross-service span timelines in a tracing backend) isn't what's being asked for here — "traceable back to what caused it and who initiated it" is fully satisfied by plain ids in the JSON envelope, joinable with jq/DuckDB/lnav. Revisit OTel only if/when you need latency-focused distributed tracing rather than causal-chain reconstruction.

**Log-search tool to adopt: VictoriaLogs**, run as a single container via docker compose, fed by tailing/shipping the existing JSON-lines files (Vector or a simple curl-based shipper into its HTTP ingestion API). It gives indexed arbitrary-field queries (LogsQL) on `correlation_id`/`causation_id`/`actor`/`client_order_id` etc., the smallest RAM/disk footprint of the server-based options benchmarked here, and a single-binary docker-compose footprint appropriate for an 8GB box shared with the rest of the trading stack. Keep `jq` for ad hoc live tailing and `DuckDB` (`read_ndjson_auto('*.jsonl')`) for retrospective SQL joins across multiple services' log files when reconstructing a full causal chain end to end.
